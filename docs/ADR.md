# Architecture Decision Records

## 철학

MVP 속도 최우선. 외부 의존성 최소화. **결정론적으로 풀 수 있는 문제를 LLM에 맡기지 않는다.**

여기에는 대안을 놓고 실제로 고른 것만 적는다. "금액은 정수로 다룬다" 같은 건 결정이 아니라 규칙이고 `ARCHITECTURE.md`의 불변 규칙에 있다. 같은 내용을 두 곳에 적으면 고칠 때 한쪽이 남는다.

---

### ADR-001: 집계·탐지는 코드, LLM은 매핑·분류·문장 생성만

**결정**: 합계·평균·비율·추이 집계와 구독·이상거래 탐지를 전부 SQL 또는 TypeScript 순수 함수로 계산한다. Claude는 (1) CSV 컬럼 매핑 추론, (2) 거래 카테고리 분류, (3) 이미 계산된 숫자를 설명하는 문장 생성만 한다.

**이유**: LLM은 산술을 틀린다. 가계부에서 총액이 틀리면 제품 전체의 신뢰가 무너진다. "구독 결제 4건, 월 47,000원"은 SQL이 100% 맞히지만 LLM은 놓치거나 지어낸다. 반대로 "지난달 대비 배달 지출이 40% 늘었다"를 자연스럽게 쓰는 건 LLM이 낫다. 각자 잘하는 것만 시킨다.

**트레이드오프**: LLM에게 자유롭게 분석을 맡겼을 때 나올 법한 예상 밖의 통찰을 포기한다. 대신 화면에 뜨는 모든 숫자가 검증 가능해진다. 이 제품에서는 후자가 압도적으로 중요하다.

### ADR-002: 카테고리는 고정 12개 enum

**결정**: 카테고리를 `src/types/category.ts`의 12개로 고정한다. structured outputs의 enum으로 LLM 출력을 강제하고, DB에도 `CHECK` 제약을 건다. 사용자는 개별 거래의 분류를 바꿀 수 있지만 카테고리 자체를 추가할 수 없다.

**이유**: LLM이 카테고리를 자유 생성하면 1월엔 "배달음식", 2월엔 "음식배달"이 나온다. 그러면 **기간별 추이가 그 자리에서 깨진다.** 추이는 Pro의 핵심 기능이므로 이건 부가 기능 하나가 아쉬운 문제가 아니라 제품이 성립하지 않는 문제다.
DB CHECK 제약까지 거는 이유는, enum 강제가 뚫렸을 때(후행 공백 등) 조용히 통과해 유령 카테고리가 차트에 생기는 걸 막기 위해서다. 방어선이 하나면 그게 뚫렸을 때 알 방법이 없다.

**트레이드오프**: "반려동물" 같은 개인화된 카테고리를 못 만든다. 사용자별 enum을 프롬프트에 넣으면 가능하지만 프롬프트 캐싱이 깨지고 구현이 복잡해진다. MVP에서는 12개로 대부분의 지출이 커버된다고 보고 표현력을 포기한다.

### ADR-003: CSV 컬럼 매핑을 LLM이 추론하고 사용자가 확인

**결정**: 은행·카드사별 파서를 만들지 않는다. 첫 20행을 로컬에서 검사해 컬럼 인덱스·허용된 의미 label·값 형식 enum만 Claude에 보낸다. 원본 헤더·셀 값은 보내지 않는다. 추론한 매핑을 사용자가 확인하며 근거가 부족한 컬럼은 수동 선택한다.

**이유**: 국내 카드사·은행 CSV는 컬럼명, 헤더 위치, 인코딩, 상단 요약행이 제각각이고 예고 없이 바뀐다. 5개사 파서를 하드코딩하면 미지원 은행 사용자는 아예 쓸 수 없고, 포맷이 바뀔 때마다 배포해야 한다. LLM 추론은 처음 보는 포맷에도 대응한다.
사용자 확인 단계를 두는 이유는 추론이 틀릴 수 있어서다. 확인 없이 진행하면 잘못된 컬럼으로 파싱한 데이터가 조용히 쌓인다.

**트레이드오프**: 생소한 헤더는 unknown으로 축약되므로 자동 매핑률이 낮아질 수 있다. 개인정보를 먼저 전송하고 나중에 파싱에서 제거하는 순서로 되돌리지 않는다. 동일 출처·파일 해시는 저장된 매핑을 재사용한다. 매핑이 확실해도 거래 유형·중복 후보가 미해결이면 사용자 확인이 필요하다.

### ADR-004: 원본 CSV를 Storage에 보관한다

**결정**: 업로드된 원본 파일을 Supabase Storage(private 버킷 + RLS)에 저장한다. 파싱 결과만 저장하고 원본을 버리지 않는다.

**이유**: 매핑이 틀렸을 때 재파싱하려면 원본이 있어야 한다. 파싱 로직을 고쳤을 때 과거 업로드를 다시 처리할 수도 있다. 원본이 없으면 사용자에게 "파일을 다시 올려주세요"라고 해야 하는데, 카드사에서 CSV를 받아 오는 게 이 제품의 최대 마찰 지점이다.

**트레이드오프**: 계좌번호·카드번호가 포함된 원본이 서버에 남으므로 유출 표면이 커진다. private 버킷 + 폴더 단위 RLS로 막고, 경로에 사용자 입력을 넣지 않으며, 재다운로드 기능을 만들지 않는다. 삭제 시에는 Storage 파일과 파생 거래를 함께 지운다.

### ADR-005: Free/Pro 경계를 시간축에 둔다

**결정**: Pro 가치의 축을 시간에 둔다 — 기간별 추이, 구독 누수 탐지, 이상거래 탐지, AI 절약 인사이트, 리포트 내보내기를 Pro로 묶는다. 여기에 더해 **Free는 KST 캘린더 월 기준 업로드 1회**로 제한한다. 자동 분류와 해당 월 요약은 Free에도 제공한다. 별개로 모든 플랜에 모델 호출 운영 한도(사용자당 UTC 하루 300회·분당 20회, 매핑·분류·인사이트·재시도 합산)를 적용한다.

**이유**: 여러 달치가 쌓여야 의미가 생기는 기능을 Pro로 묶으면, Free 사용자가 데이터를 쌓는 행위 자체가 전환 훅이 된다. 업로드 횟수 제한을 얹은 것은 그 위에 명확한 유료 전환 지점을 하나 두기 위한 결정이다.

두 한도의 기준 시각이 다른 것은 의도적이다. **업로드 한도는 KST 캘린더 월**을 쓴다 — 사용자에게 "이번 달 1회"로 보이는 약속이므로 사용자의 달력과 일치해야 한다. **호출 한도는 UTC**를 쓴다 — 내부 비용 통제 장치라 사용자에게 노출되지 않는다. 두 규칙을 하나로 합치면 한쪽이 사용자에게 어색해진다.

**트레이드오프**: 월별 파일이 3개월치 따로 있는 Free 사용자는 세 달에 걸쳐 올려야 한다. **이건 실제 마찰이다** — 완화 장치로 ① 한 파일에 여러 달이 들어 있으면 1회로 계산한다(행 수 상한 10,000까지) ② 같은 출처의 동일 파일 재업로드는 기존 업로드를 반환하며 횟수를 소비하지 않는다 ③ 한도 도달 시 남은 일수와 함께 Pro 전환을 안내한다. 이 완화가 없으면 Free가 제품을 평가할 기회조차 잃는다.

### ADR-006: 분류는 1요청 = 1배치, 클라이언트가 순차 오케스트레이션

**결정**: `/api/transactions/classify`는 사용자별 LLM lease 획득 후 미분류 지출/환불 최대 50건을 선택하고 사용량 예약 후 처리한다. 서버는 배치 루프를 돌지 않는다. 클라이언트는 진행률을 표시하며 한도·오류·무진척 시 반복을 멈춘다. UPDATE의 NULL 조건은 사용자 수정을 보존하며 동시 모델 호출 방지는 lease가 담당한다.

**이유**: 300건이면 6배치다. 배치별 요청으로 진행률·부분 성공을 전달하고 실패한 배치부터 재개한다. 한 요청이라고 이미 커밋한 앞 배치가 자동 롤백되는 것은 아니다.
**함수 타임아웃 때문이 아니다.** Vercel은 fluid compute 기준 Hobby도 300초라 한 요청에 몰아도 시간 자체는 충분하다. 이걸 명시해두는 이유는, 나중에 "타임아웃을 늘리면 되잖아"라는 이유로 이 결정이 잘못 뒤집히는 걸 막기 위해서다.

**트레이드오프**: 브라우저를 닫으면 분류가 중단된다. 큐나 크론으로 서버에서 완주시킬 수 있지만 인프라가 하나 늘어난다. 미분류 거래는 DB에 남으므로 다음 방문 때 이어서 처리되고, 그 사이 대시보드에는 미분류로 표시된다. MVP에서는 이 정도 손실이 큐를 들이는 비용보다 싸다.

### ADR-007: Tailwind v4 `@theme` 토큰 + `[data-theme]` 변수 덮어쓰기

**결정**: 색상을 `@theme`의 `--color-*`로 선언해 유틸리티(`bg-surface`, `text-muted`)를 자동 생성시키고, `[data-theme="dark"]`에서 같은 변수를 덮어쓴다. **`dark:` variant를 쓰지 않는다.**

**이유**: 라이트/다크 양쪽을 지원할 때 `dark:` variant를 쓰면 모든 요소에 클래스가 두 벌씩 붙고, 한쪽만 빠뜨려도 눈으로 봐야 발견된다. 변수를 갈아끼우는 방식은 클래스가 한 벌이라 빠뜨릴 곳이 없다.
`@theme`를 쓰는 부수 효과로 컴포넌트에서 hex를 하드코딩할 이유가 사라진다. 여러 phase에 걸친 독립 세션들이 컴포넌트를 만드는 구조에서 이건 중요하다 — 토큰명으로만 색을 지정할 수 있으면 세션마다 다른 회색을 쓰는 일이 생기지 않는다.

**트레이드오프**: v3 문법(`bg-[--surface]`)과 `tailwind.config.js` 자산을 못 쓴다. 특히 v3 문법은 v4에서 **에러 없이 조용히 무시되므로** 섞여 들어오면 발견이 늦다. UI_GUIDE에 경고를 명시했다.

### ADR-008: 업로드 삭제는 CASCADE 유지, 대신 명시된 동작으로 문서화

**결정**: `transactions.upload_id`에 `ON DELETE CASCADE`를 유지한다. 기간이 겹치는 CSV를 여러 개 올린 경우 겹치는 거래는 먼저 올린 업로드에만 귀속되므로, 그 업로드를 지우면 나중 파일에도 있던 거래가 함께 사라진다. 이를 **삭제 확인 UI에서 사용자에게 알린다.**

**이유**: 정확한 해법은 `transaction_sources(transaction_id, upload_id)` 조인 테이블이다. 그러면 어떤 업로드를 지워도 다른 업로드가 제공한 거래는 남는다. 하지만 테이블 하나, 조인 하나, 삭제 시 "다른 출처가 있는지" 확인하는 로직이 붙는다. MVP에 비해 무겁다.
더 중요한 건, PRD가 사용자에게 약속한 것이 "삭제하면 지워진다"라는 점이다. CASCADE는 그 약속을 지킨다.

**트레이드오프**: "1월 파일만 지웠는데 2월 숫자가 바뀌었다"를 겪을 수 있다. 이걸 감수하는 조건은 하나 — **버그로 발견되게 두지 않는 것.** 삭제 확인 화면이 "이 업로드에서 가져온 거래 N건이 함께 삭제됩니다. 다른 파일에도 있던 거래라면 그 파일을 다시 올려야 복구됩니다"를 표시해야 이 결정이 성립한다.

### ADR-009: 출처별 식별과 불확실한 중복의 사용자 확인

**결정**: financial_sources로 카드/계좌를 구분한다. 같은 출처·동일 파일은 재사용하고, 승인된 거래 고유번호는 유형·청구월과 함께 중복 키로 쓴다. 고유번호 없는 서로 다른 파일의 유사 행은 사용자가 확인한다. 파일 내 순번은 파일 간 식별자가 아니다.

**이유**: 날짜·금액·가맹점이 같은 정상 결제와 중복 수입을 구분할 수 없는 경우가 있다. 자동 제거보다 정상 거래 보존을 우선한다. 원본 카드/계좌번호 대신 서버 생성 출처 UUID로 범위를 나눈다.

**트레이드오프**: 출처 테이블과 중복 확인 UI가 추가된다. 기존의 4테이블 제한은 해제하며, 사용량 테이블까지 총 6개가 된다. 상세 해시식·권한·호출 한도는 ARCHITECTURE가 단일 기준이다.

### ADR-010: 툴체인 버전을 최신이 아닌 상태로 고정한다

**결정**: 아래 버전을 `package.json`에 정확한 값으로 박고 올리지 않는다.

| 패키지 | 고정 | 최신 | 고정 사유 |
|---|---|---|---|
| `eslint` | 9.39.5 | 10.10.0 | `eslint-config-next@16.3.4`가 번들한 플러그인(`eslint-plugin-import`·`jsx-a11y`·`react`·`react-hooks`·`typescript-eslint`)의 peer가 **eslint ^9에서 끊긴다.** 10을 넣으면 `npm ls`가 전부 `invalid`로 표시한다 |
| `vitest` | 4.1.11 | 5.0.0 | Vitest 5는 Node `^22.12 \|\| ^24 \|\| >=26`을 요구한다. 개발 환경이 Node 20.20.0이라 **설치해도 실행되지 않는다** |
| `typescript` | 5.9.3 | 7.0.2 | 7은 컴파일러를 Go 네이티브로 재작성한 새 메이저다. typescript-eslint·타입 생성 도구에 미지의 공백이 있을 수 있다 |
| `@types/node` | 20.19.43 | 26.5.0 | @types/node 메이저는 Node 메이저를 따른다. 26을 쓰면 **Node 20에 존재하지 않는 API가 타입 검사를 통과**해 런타임에서만 터진다 |

Next.js는 반대로 **16.3.4(최신)** 를 쓴다. 생짜로 시작하는 프로젝트를 이전 메이저에 고정할 이유가 없고, Node 20.9+ 요구를 개발 환경이 만족한다.

**이유**: Stop 훅이 매 세션 종료마다 `lint && build && test`를 돌리고 TDD 훅이 매 편집마다 돈다. 툴체인이 흔들리면 제품 코드가 아니라 도구를 디버깅하느라 개발이 멈춘다. 그리고 각 step은 독립 세션이므로, 어느 세션이 "ESLint가 구버전이네" 하고 올리면 그 뒤 모든 step의 lint가 깨진다.

**트레이드오프**: 최신 성능 개선을 못 쓴다. 특히 TypeScript 7의 컴파일 속도 향상은 Stop 훅의 build 시간에 직접 도움이 됐을 것이다. Node를 22 이상으로 올리면 Vitest 5·`@types/node` 22 제약이 풀리므로 그때 이 ADR을 갱신한다.

### ADR-011: 카테고리 분류는 규칙 사전을 먼저 태우고 LLM은 폴백으로만 쓴다

**결정**: 분류를 3단으로 처리한다. ① `merchant_rules`(사용자가 거래를 수정해 만든 규칙) ② 내장 가맹점 규칙 사전(`src/lib/merchant-rules.ts`, 부분 문자열 매칭) ③ 위 둘이 못 잡은 가맹점만 Claude 배치 분류. 결과는 `category_source`에 `'user' | 'rule' | 'ai'`로 기록한다.

**이유**: ADR-001이 "결정론적으로 풀 수 있는 문제를 LLM에 맡기지 않는다"고 정했다. "스타벅스 → 카페/간식"은 결정론적으로 풀 수 있는 문제다. 규칙 사전을 먼저 태우면 ① 실 명세서의 상당 부분이 LLM 호출 0회로 분류돼 ADR-005의 호출 한도 안에서 여유가 생기고 ② 그 부분은 순수 함수 단위 테스트로 고정되며 ③ 같은 가맹점이 배치마다 다르게 분류되는 일이 구조적으로 불가능해진다.

`merchant_rules`를 최우선에 두는 이유는 사용자가 고친 것이 우리 사전이나 LLM보다 항상 옳기 때문이다. 사용자 수정이 사전을 스스로 키워주는 구조가 된다.

**트레이드오프**: 내장 사전을 유지보수해야 하고, 사전에 없는 신규 가맹점은 여전히 LLM을 탄다. 사전이 틀린 매칭을 하면(`"쿠팡이츠"`를 `"쿠팡"` 규칙이 먼저 잡는 등) LLM보다 나쁜 결과가 나오므로 **더 구체적인 패턴이 먼저 오도록 정렬하고 첫 매칭에서 멈추는 규약**을 테스트로 고정해야 한다. 정규표현식은 쓰지 않는다 — 가맹점명에 `(`·`)`·`*`가 실제로 들어있어 이스케이프 사고가 난다.
