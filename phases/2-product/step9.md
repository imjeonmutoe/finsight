## 작업

담당 화면: **S11**(`/dashboard/uploads`) · **S12**(`/dashboard/settings`).

### S11 — 업로드 이력

목록에 표시할 것: 카드/계좌 별칭, 파일명, 업로드 일시, 상태, 거래 건수, 중복 건수.

**상태별 처리:**
- `parsed` — 정상. 삭제 가능
- `mapped` — **"미완료"로 구분 표시.** 사용자가 매핑 확인 화면에서 이탈해 Storage에 파일만 있고 거래는 0건인 상태다. **"이어서 진행" 버튼**으로 `/dashboard/upload?resume={id}`로 보내고, 삭제도 가능하게 한다. 이게 없으면 고아 파일이 Storage에 계속 쌓인다
- `failed` — 에러와 함께 재시도·삭제 제공. 같은 파일의 기존 행/Storage를 재사용하고 LLM 한도는 그대로 적용
- `pending` — 처리 중. 요청 제한시간과 lease 만료 후에도 남아 있으면 failed로 전환해 재개

**삭제 확인 — ADR-008의 조건이다.**

CASCADE 유지를 감수하는 유일한 조건이 "버그로 발견되게 두지 않는 것"이다. 삭제 확인 다이얼로그에 반드시 표시한다:

> 이 업로드에서 가져온 거래 **N건**이 함께 삭제됩니다.
> 다른 파일에도 있던 거래라면 그 파일을 다시 올려야 복구됩니다.

N은 서버에서 실제로 세어 온 값이어야 한다. 추정치를 쓰지 마라.

**브라우저 `confirm()`이나 `alert()`을 쓰지 마라.** 인라인 다이얼로그 컴포넌트로 만든다.

### S12 — 설정

- **플랜 표시** — 현재 플랜(Free/Pro). 업그레이드·관리 버튼은 step 11에서 이 페이지에 덧붙인다. 여기서는 플랜 표시까지만 하고 결제 관련 UI는 만들지 않는다
- **금융 데이터 삭제** — 확인 문구 입력(예: "삭제"를 타이핑) 후 실행하는 Destructive 액션. 원본·거래·규칙·출처를 초기화하며 계정·구독·모델 호출 사용량은 유지됨을 안내한다

**전체 삭제 순서: Storage → DB.**
`auth.users` 삭제의 CASCADE는 Storage 객체를 지우지 않는다. Storage를 먼저 비우고 DB를 지운다. 순서가 반대면 DB 레코드가 사라져 어떤 파일을 지워야 할지 알 수 없게 되고 고아 객체가 영구히 남는다.

삭제 대상: Storage의 해당 사용자 폴더 전체 + `transactions` + `uploads` + `merchant_rules` + `financial_sources`. `profiles`와 `llm_usage`는 유지한다. 이 버튼을 계정 삭제로 구현하지 않는다. 계정 삭제 요청은 개인정보처리방침의 문의 경로로 접수한다.

삭제 전 안내에 **"Anthropic에 이미 전송된 데이터는 회수할 수 없습니다"**를 명시한다(개인정보처리방침과 일관되게).

## 금지사항

- 삭제 확인에서 영향 건수를 생략하지 마라. 이유: ADR-008이 CASCADE를 유지하는 조건이 이 고지다. 없으면 "1월 파일만 지웠는데 2월 숫자가 바뀌었다"가 버그로 신고된다.
- 브라우저 `confirm()`·`alert()`을 쓰지 마라. 이유: 스타일을 못 맞추고, 자동화 도구에서 세션을 멈춘다.
- 전체 삭제를 DB 먼저 하지 마라. 이유: Storage 객체가 영구 고아가 된다.
- 원본 CSV 재다운로드 기능을 만들지 마라. 이유: signed URL 만료 관리와 유출 표면을 MVP에 들이지 않기로 했다(ARCHITECTURE 보안 섹션).
- 결제·플랜 변경 UI를 만들지 마라. 이유: step 11이 이 페이지에 덧붙인다. 여기서 만들면 중복된다.
- 삭제 API를 새로 만들지 마라. 이유: step 7의 `DELETE /api/uploads/[id]`를 쓴다. 전체 삭제만 새로 만든다.
